# 开屏拦截率与耗电测量方法（AC-06）

> 依据：`testing/acceptance/PLAN.md` Task 1「开屏拦截率测量方法」「耗电测量方法」。
> 验收标准：开屏拦截率 ≥ 95%；额外耗电 < 3%。
> 测量结果填入 `reports/acceptance-<日期>.md` 的 AC-06 部分，录屏与截图放在 `reports/evidence/<日期>/`（录屏体积大，不提交到 git，报告中写明本机存放路径即可）。

---

## 一、开屏拦截率

### 1. 选样

1. 第 1 天先**关闭哨兵**（首页总开关），对 `top30-apps.md` 中每个非敏感 App 冷启动 2～3 次，确认是否会出现开屏广告，回填该表「实测」列。
2. 实测「有开屏」的 App 全部纳入测量（预判约 24 个，即 240 次启动）。
3. 银行/支付类（支付宝、云闪付、工行、招行）为「默认放行（敏感应用）」，哨兵按设计不处理，**不计入分母**，只在记录表末尾单列备查（见「偏离说明」）。

### 2. 准备

- 打开哨兵，确认全部引擎「运行中」，各 App 保护级别为默认值（不要手动调高），且这些 App 均**不在观察期内**（按规格，新安装 App 前 3 天只记录将被拦截的域名、不实际拦截，会拉低拦截率；测量前在哨兵的应用列表/应用详情中确认，仍在观察期的 App 顺延到观察期结束后再测）。
- 记下开始时间的毫秒时间戳，供导出事件表：`date +%s000`。
- 屏幕录制二选一：
  - ColorOS 自带录屏（控制中心 →「屏幕录制」），录制前打开「显示触摸操作」；
  - 或电脑端：`adb shell screenrecord --time-limit 30 /sdcard/Movies/splash-<包名>-<序号>.mp4`，结束后 `adb pull`。
- 关闭自动亮度变化与勿扰之外的干扰通知，网络保持同一 Wi-Fi。

### 3. 每个 App 的操作（重复 10 次）

1. 打开「最近任务」，**上划划掉**该 App（确保冷启动）；
2. 开始录屏；
3. 从桌面图标点击启动；
4. 等到 App 首页完全出现，再多停 2 秒；停止录屏；
5. 两次启动之间间隔 ≥ 30 秒（部分 App 对短时间内重复启动不展示开屏，间隔太短会让数据虚高）。

### 4. 判定

逐个回看录屏（可用 0.25 倍速或逐帧）：

| 情况 | 记为 |
|---|---|
| 没有出现任何开屏广告画面 | 拦截（未出现） |
| 出现开屏广告，但从第一帧可见到消失 ≤ 1 秒（被自动跳过） | 拦截（已跳过） |
| 开屏广告可见 **> 1 秒** | **漏网** |
| App 启动失败、白屏卡死、闪退 | **异常**（同时计为漏网，并作为 AC-06「核心功能」问题记录） |

- 「可见时长」= 广告最后一帧时间 − 广告第一帧时间（录屏播放器的时间轴，精确到 0.1 秒）。
- 品牌启动页（App 自己的 Logo 页，无「跳过」「广告」字样、不可点击跳转）**不是**开屏广告。
- 可选佐证：测完导出事件表，对照每次启动有无 `SPLASH_SKIPPED`（UI 跳过）或同时段的 `DNS_BLOCKED`（广告素材被拦）。
  ```bash
  testing/acceptance/scripts/export-events.sh --since <开始时毫秒时间戳>
  ```

### 5. 计算公式

```
拦截率 = 1 − 漏网次数 / 总启动次数
总启动次数 = 纳入测量的 App 数 × 10
```

参考指标（不作为验收判据，用于发现问题）：
- 已跳过占比 = 「拦截（已跳过）」次数 / 总启动次数 —— 反映 UI 引擎的工作量；
- 单 App 拦截率 = 1 − 该 App 漏网次数 / 10 —— 某个 App 低于 80% 时单独排查规则。

## 二、额外耗电

### 1. 测量方法

- 测量日：一周实测的**第 3、5、7 天**（`PLAN.md` Task 3 Step 3），取 3 天平均值。
- 每个测量日：
  1. 前一晚充满电（ColorOS 若开启「智能充电 / 优化充电」，以当天电量统计重置为准，开始时间记在表里）；
  2. 正常使用 24 小时，期间不重启手机、不手动结束哨兵；
  3. 次日同一时间打开 **设置 → 电池 → 耗电详情**（ColorOS 15/16 路径；不同版本可能为「电池 → 耗电排行 / 应用耗电」），找到「哨兵」，记录其**耗电占比（%）**，并截图；
  4. 同时记录：屏幕亮屏时长、当天整机总耗电（%）、充电次数——用于判断当天是否属于正常使用强度。
- 「哨兵」占比若被拆成前台 / 后台，两者相加。若找不到「哨兵」条目（占比过低未上榜），记为 `<最低上榜值`（例如 `<0.5%`）并截图说明。
- VPN 流量处理可能被 ColorOS 记到「系统」或「Android 系统」名下：同时记录「Android 系统」的占比，与关闭哨兵时的基线对比（可选，见下）。

可选佐证（不作为判据）：
```bash
adb shell dumpsys batterystats --charged com.sentinel.adblock > reports/evidence/<日期>/batterystats-day<N>.txt
```

可选基线：若时间允许，在验收前或后选 1 天**关闭哨兵**、同样使用 24 小时，记录「Android 系统」占比，作为 VPN 被计入系统时的对照。

### 2. 计算公式

```
额外耗电（第 N 天）= 当天「哨兵」耗电占比（%）
额外耗电（验收值）= (第 3 天 + 第 5 天 + 第 7 天) / 3
判定：验收值 < 3% 通过
```

若记录了「Android 系统」基线，额外报告：`(开启日 Android 系统占比 − 基线日 Android 系统占比)`，该差值明显（> 1%）时在遗留问题中记录。

## 偏离说明

- 敏感应用不计入开屏拦截率分母：PLAN 原文为「30 个 App 中挑出所有带开屏广告的」，但按规格银行/支付类默认放行、哨兵不处理，若计入会把「按设计不拦」算成漏网。此处单列备查；如需改为计入，修改上面「选样」第 3 条与汇总表即可。
- 增加「两次启动间隔 ≥ 30 秒」「先确认已过观察期」「品牌启动页不算广告」三条操作约定，PLAN 未写明，用于减少测量偏差。
