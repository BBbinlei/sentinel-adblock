# 「哨兵」广告拦截软件 设计文档

- 日期：2026-10-01
- 状态：待用户审阅
- 目标设备：OPPO Find X7 Ultra（ColorOS 15/16，Android 15/16）
- 选定方案：方案二「哨兵」——模块化、全本地、可扩展

---

## 1. 目标与边界

### 1.1 目标
1. 覆盖调研清单中的全部 27 种广告套路（见第 9 节映射表）。
2. **拦截广告的同时，不影响原软件的正常使用**——这是最高优先级约束，与拦截率冲突时以它为准。
3. 前端美观、简洁、易操作：家人只用首页大开关 + 每个 App 的三档开关即可。

### 1.2 使用范围
- 第一阶段：作者本人自用。
- 第二阶段：家人使用（直接安装 APK，不上架应用商店）。
- 不做云端服务器、不做账号、不对外分发规则。

### 1.3 约束
- **不依赖 root**。Find X7 Ultra 存在 BL 熔断风险（社区资料：16.0.3.500 / 16.0.8.xxx 两次不可逆熔断，待实机核实）。在核实前，**不要升级系统**。
- 特权操作全部通过 Shizuku（无线调试激活）完成。
- 不做 HTTPS 中间人解密（Android 7+ App 默认不信任用户证书，无效且有安全风险）。

### 1.4 非目标
- 不拦截浏览器网页内广告的元素级隐藏（可后续扩展）。
- 不支持 OPPO 以外机型（架构上预留 ColorOS 配置档案机制，其他品牌后续可加档案）。

## 2. 技术栈

| 层 | 选型 |
|---|---|
| 语言 | Kotlin，协程 + Flow |
| 界面 | Jetpack Compose + Material 3（动态取色、深色模式）+ Navigation Compose |
| 网络拦截 | VpnService（仅接管 DNS + 指定 IP 段） |
| 界面层拦截 | AccessibilityService |
| 系统净化 | Shizuku UserService（pm / appops / settings / dumpsys） |
| 通知过滤 | NotificationListenerService |
| 存储 | Room（`enableMultiInstanceInvalidation` 多进程共享）、规则二进制文件（mmap） |
| 后台任务 | WorkManager |
| 依赖注入 | Koin |
| 序列化 | kotlinx.serialization |

### 2.1 已采纳的 8 项后端优化
1. HttpDNS 拦截回快速拒绝（TCP RST / ICMP 不可达），不静默丢包，避免 App 超时卡顿。
2. 规则预编译为排序二进制，mmap 加载；匹配按域名后缀逐级查（≤5 次）。
3. 无障碍引擎按「包名 + Activity」建规则索引，只监听窗口变化事件并防抖；开屏规则仅在冷启动后数秒内生效。
4. Shizuku「执行一次、长期生效」：只在执行和巡检时需要，重启后无需常驻。
5. 进程精简为两个：主进程 + `:vpn` 进程。
6. 进程间不写 AIDL，通过共享 Room + Flow 同步配置。
7. 依赖注入用 Koin，不用 Hilt。
8. 核心逻辑（规则解析/编译/匹配/选择器、guard 决策）为纯 Kotlin 模块，JVM 上直接单测。

## 3. 整体架构

```
界面层     :app            Compose 界面、引导向导
             ↕ 读写配置 / 订阅状态
数据层     :data           Room、WorkManager 规则订阅
             ↕ 多进程共享
引擎层     主进程：  :engine-a11y    无障碍点击
                    :engine-notify  通知过滤
                    :engine-system  Shizuku 系统净化 + ColorOS 配置档案
           :vpn 进程：:engine-vpn    DNS 过滤 + HttpDNS 拒绝 + 守护
核心层     :core-rules     纯 Kotlin：规则解析、编译、匹配、选择器
           :guard          健康守护、操作日志与撤销、自动降级
```

### 3.1 模块职责

| 模块 | 职责 | 依赖 |
|---|---|---|
| `:app` | 界面、向导、快捷开关 | `:data` |
| `:data` | Room 实体与 DAO、订阅下载、规则编译调度 | `:core-rules` |
| `:core-rules` | 规则格式定义、解析（AdGuard/hosts/GKD 订阅）、编译、域名匹配、选择器匹配 | 无（纯 Kotlin） |
| `:guard` | 误伤判定、自动降级、操作日志、撤销 | `:data`，决策逻辑纯 Kotlin |
| `:engine-vpn` | DNS 过滤、HttpDNS 拒绝、观察期记录、守护其他服务 | `:core-rules` `:data` |
| `:engine-a11y` | 开屏跳过、弹窗关闭、激励视频处理、跳转回退、学习模式 | `:core-rules` `:data` |
| `:engine-notify` | 营销通知过滤 | `:core-rules` `:data` |
| `:engine-system` | 执行安全清单内的系统操作、巡检漂移、ColorOS 配置档案 | `:data` |

原则：**引擎只负责识别和执行，规则统一来自 core-rules，误伤统一交给 guard 处理。** 引擎把误伤信号写入数据层 `signals` 表，guard 订阅处理，因此引擎不直接依赖 guard。

## 4. 前端交互设计

### 4.1 导航
```
首次启动 ──► 引导向导（5 步） ──► 主界面（底部 3 个页签：首页 / 应用 / 规则）
任何时候：通知栏常驻快捷开关 [暂停拦截 5 分钟]
```

### 4.2 引导向导
① 激活 Shizuku → ② VPN 授权 → ③ 无障碍 + 允许受限设置 → ④ 通知使用权 → ⑤ 电池白名单 + 锁定后台。
- 每步有图示，点「去设置」跳转对应系统页，返回后自动检测是否完成。
- 每步可跳过；首页对未完成项持续显示提示，可随时补做。

### 4.3 首页
```
┌─────────────────────────┐
│        🛡️ 防护中         │  ← 点击 = 全部暂停 / 恢复
│     今日拦截  1,284      │
├─────────────────────────┤
│ 🌐 网络拦截   ● 正常     │  → 拦截日志
│ 👆 自动跳过   ● 正常     │  → 跳过日志
│ 🔔 通知过滤   ● 正常     │  → 过滤日志
│ 🧹 系统净化   ⚠ 2项待处理 │  → ColorOS 广告项清单
├─────────────────────────┤
│ ⚠ 「XX」疑似受影响，      │  ← guard 提醒
│   已自动降级  [查看][撤销]│
└─────────────────────────┘
```
系统净化清单：每项显示状态；Shizuku 能处理的「一键处理」，只能在 UI 中关闭的「去关闭」直达设置页；底部「撤销记录」。

### 4.4 应用页
- 列表：搜索；按拦截次数排序；银行/支付类默认「关」。
- 详情：
  - **拦截级别**：`关 / 标准 / 强力`（家人只碰这个）。
  - **高级（默认折叠）**：开屏广告、激励视频（`静默播完 / 直接拦截 / 每次询问`）、摇一摇跳转、跳转回退、营销通知。
  - 「App 打不开？一键临时放行」（放行 24 小时，同时触发 guard 记录）。

### 4.5 运行中交互
- 跳转回退：底部小提示「已拦截 A → B 的跳转 [撤销]」，3 秒消失；撤销 = 打开 B + 记为例外。
- 激励视频设为询问：识别到激励视频页时弹出「静默播完 / 正常观看 / ☐记住」（此时视频已加载，无法再拦截；需要拦截请设为「直接拦截」）。
- 学习模式：用户手动关闭弹窗后，通知询问「以后自动关？」，确认则生成本地规则。

### 4.6 规则页
订阅列表（条数、更新时间、启停）、我的规则（学习生成，可编辑删除）、添加订阅、立即更新。

### 4.7 交互原则
1. 家人只需首页大开关 + 三档开关，高级选项折叠。
2. 每个自动执行的动作都可撤销。
3. 出了问题最多点两下就能放行。

## 5. 后端模块详细设计

```
┌──────────── 主进程 ────────────┐  ┌──── :vpn 进程 ────┐
│ engine-a11y                    │  │ engine-vpn         │
│  ├ 规则索引（包名+页面）        │  │  ├ DNS过滤（mmap） │
│  ├ 开屏跳过 / 弹窗关闭          │  │  ├ HttpDNS快速拒绝 │
│  ├ 激励视频：静音+等播完+关闭   │  │  ├ 观察期：只记录   │
│  └ 跳转回退（3条件同时满足）    │  │  └ 守护：拉起其他服务│
│ engine-notify  关键词/渠道过滤  │  └─────────┬─────────┘
│ engine-system  Shizuku+安全清单 │            │
└───────────────┬────────────────┘            │
                ▼                             ▼
        ┌───── data（Room 多进程共享）─────┐
        │ 规则 / 配置 / 事件 / 操作日志     │
        └──────┬───────────────────┬──────┘
               ▼                   ▼
          core-rules            guard
```

### 5.1 core-rules
- **规则分级**：
  - `标准` 级：只含「纯广告域名」（仅用于投放广告、不承载正常内容的域名），人工维护的精选白名单校验过。
  - `强力` 级：在标准级基础上加入完整订阅（anti-AD、AWAvenue 等）。
- **统一规则模型**：一条规则 = `{id, 类型(dns/ui/notify), 作用范围(全局/包名/页面), 匹配条件, 动作, 级别, 来源}`。
- **解析器**：AdGuard/hosts 域名格式、GKD 订阅格式（选择器）、自定义 JSON。
- **编译**：域名规则 → 排序后缀表二进制；UI 规则 → 按包名 + Activity 的索引。
- **永不拦截名单**：系统内置（支付、银行、系统更新、推送通道等关键域名），任何级别都不会命中。

### 5.2 engine-vpn（`:vpn` 进程）
- 只把 DNS 服务器地址和 HttpDNS IP 段路由进 TUN，其他流量不经过 VPN。
- DNS 查询：命中规则 → 返回 `0.0.0.0`/NXDOMAIN；未命中 → 转发上游（DoH，带缓存）。
- HttpDNS：域名层拦截 + 已知 IP 段快速拒绝（TCP RST / ICMP 不可达），迫使 App 回退系统 DNS。
- 分应用：银行/支付类及用户设为「关」的 App 通过 `addDisallowedApplication` 完全不经过 VPN。
- **观察期**：新安装 App 前 3 天只记录将被拦截的域名、不实际拦截；期满后 guard 评估无异常再启用。
- **守护**：作为前台服务常驻，定期检查无障碍、通知监听是否存活，失效时提示用户（系统服务无法被普通 App 强制拉起，只能提醒或引导）。

### 5.3 engine-a11y（主进程）
- 只监听 `TYPE_WINDOW_STATE_CHANGED` / `TYPE_WINDOW_CONTENT_CHANGED`，按当前「包名 + Activity」查索引，无规则直接返回；防抖 ≥100ms。
- **开屏跳过**：冷启动后 5 秒内生效，匹配「跳过」类节点并点击。
- **弹窗关闭**：精确匹配真关闭按钮（排除伪关闭、排除「下载 / 确认」类节点）；检测到预勾选「自动续费」时提醒用户。
- **激励视频**（三种模式）：
  - `静默播完`（默认）：识别激励视频页 → 临时将媒体音量降为 0 → 等倒计时结束 → 点击关闭 → 恢复音量。**奖励照常发放。**
  - `直接拦截`：交给 VPN 层拦截该 App 的激励广告域名（可能拿不到奖励，界面上明确告知）。
  - `每次询问`：弹出「静默播完 / 正常观看 / ☐记住」。
- **奖励窗口**：广告 SDK 投放域名默认被 VPN 拦截；用户点击「看视频领奖励」类按钮时打开 60 秒奖励窗口，窗口内 VPN 对该 App 放行这些域名（`直接拦截` 模式不开窗口）。
- **跳转回退**：以下三条件**同时满足**才触发——
  1. 源 App 冷启动后 5 秒内；
  2. 期间源 App 内无用户交互（以无 `TYPE_VIEW_CLICKED` / `TYPE_VIEW_SCROLLED` 事件作为判据）；
  3. 目标 App 属于电商 / 下载 / 广告常见落地类别。

  排除：从通知栏、桌面、其他 App 链接主动打开的跳转。触发后重新打开源 App，并显示可撤销提示；撤销即加入例外。
- **学习模式**：记录用户手动关闭弹窗时点击的节点特征，生成候选规则，用户确认后入库。

### 5.4 engine-notify（主进程）
- 按 App + 渠道 + 关键词规则匹配，命中则 `cancelNotification`（常驻通知无法取消，只记录）。
- 学习：用户连续手动划掉同一 App 同一渠道的通知 N 次，询问是否自动过滤。

### 5.5 engine-system（主进程）
- **安全清单**：只执行清单内的操作，每一项都必须在 Find X7 Ultra 上实测验证后才能加入。
- 操作优先级：关开关（`settings put`）> 撤销权限（`appops set`）> 禁用（`pm disable-user`）> 卸载（`pm uninstall -k --user 0`）。
- 每次操作写入操作日志（操作前状态 + 命令 + 结果），可单项或全部撤销。
- **巡检**：每天及开机后检查清单项是否被系统改回，被改回则提醒用户一键重新执行。
- **ColorOS 配置档案**：包名、settings 键、设置页 Intent 按 ColorOS 版本存储，系统升级后只需更新档案。

### 5.6 guard
- **误伤信号**：
  1. 用户在某 App 内反复撤销 / 临时放行；
  2. VPN 层出现「被拦截域名被反复重试」的重试风暴；
  3. 无障碍检测到「应用已停止运行」系统弹窗或 App 反复冷启动；
  4. （Shizuku 在线时）`dumpsys dropbox` 中出现该 App 崩溃记录。
- **处置**：定位到最近作用于该 App 的规则 → 仅对该 App 停用该规则 → 首页提醒 `[查看][撤销]`。
- 决策逻辑为纯 Kotlin，可单测。

## 6. 「不影响正常使用」的四项保障

| 风险 | 解决措施 | 预期程度 |
|---|---|---|
| 误拦正常内容 | 标准级只用纯广告域名；共用域名改由界面层处理；新 App 3 天观察期；永不拦截名单 | 基本解决，残余由 guard 兜底 |
| 激励视频拿不到奖励 | 默认「静默播完」：静音、等播完、自动关闭，奖励照拿 | 解决 |
| 跳转回退误判 | 三条件同时满足才触发；主动打开的跳转一律放过；撤销即例外 | 接近零 |
| 禁用系统组件导致功能失效 | 只执行实测过的安全清单；优先关开关不卸载；一键还原 | 解决 |

## 7. 数据流与容错

### 7.1 数据流
```
【规则流】订阅源 ─(WorkManager 每天)─► 下载 ─► 校验 ─► 编译二进制 ─► 引擎热加载
                                   失败 ↘ 继续用旧版本
【事件流】引擎拦截 ─► 写入事件(App, 套路, 规则ID) ─► 首页统计 / guard 分析
【自愈流】guard 发现异常 ─► 定位规则 ─► 对该 App 停用该规则 ─► 提醒 [查看][撤销]
```

### 7.2 容错

| 故障 | 处理 |
|---|---|
| 主进程引擎崩溃 | 系统自动重绑无障碍/通知服务；VPN 守护检测并提示 |
| VPN 进程挂掉 | 网络自动恢复直连，不会断网 |
| Shizuku 离线 | 已做改动持续生效，仅暂停巡检并提醒 |
| ColorOS 升级 | 巡检发现设置被改回，提醒一键重新执行；档案不匹配时降级为只读提示 |
| 规则文件损坏 | 校验失败自动回滚到上一版 |

**原则：任何故障只会让拦截变弱，不会让手机或 App 不能用。**

## 8. 测试方案

> 详细测试计划、测试边界与用例编号统一在 `testing/` 模块中定义（单元测试、规则回归、设备集成、实际验收四个板块），每个功能模块完成后立即执行对应的质量关卡。

| 层 | 内容 | 环境 |
|---|---|---|
| ① 单元测试 | core-rules 解析/编译/匹配、guard 决策 | JVM，秒级 |
| ② 规则回归 | 录制的广告页面节点快照 → 验证 UI 规则命中、不误命中 | JVM |
| ③ 设备集成 | VPN、无障碍、Shizuku 联调 | 模拟器 + 真机 |
| ④ 实机验收 | Find X7 Ultra，30 个常用 App，连续一周 | 真机 |

**专项测试**：
- 误拦：Top 1000 正常域名在标准级规则下 0 命中。
- 误判：20 种主动跳转场景（点链接、通知打开、分享等）0 回退。
- 激励视频：10 个 App 中「静默播完」模式奖励全部正常到账。
- 故障演练：杀引擎、断 Shizuku、注入损坏规则，网络和 App 均正常。

**验收标准**：30 个 App 核心功能全部正常；开屏广告拦截率 ≥95%；额外耗电 <3%。

## 10. 待实机核实项（实现前必须完成）

以只读命令（`pm list packages`、`settings list`、`appops get`、`dumpsys`）在 Find X7 Ultra 上确认：
